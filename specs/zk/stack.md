# ZK Proving Stack

This document pins the zero-knowledge proving stack the protocol
targets. It is a *foundation document*: every gadget, circuit, and
prover artifact in `crates/gadgets`, `crates/circuits`, and
`crates/prover` is bound by the choices here. Changing any pinned
value in this document is a workspace-scale break.

> **NOTE(name):** crate names `gadgets`, `circuits`, `prover`,
> `prover-server`, `prover-wasm` are working names. No product
> name baked in.

## What this is

A spec for the proving environment, not for any specific circuit
or gadget. Three layers of choice are pinned:

1. **Cryptographic substrate** — curve, field, proving system.
2. **Library substrate** — which arkworks crates, at which
   versions, with which feature flags.
3. **Conventions** — how gadgets are tested, how circuits are
   structured, how proofs cross the on-chain boundary.

Gadget and circuit specs live next to this document
(`specs/zk/gadget-<name>.md`, `specs/zk/circuit-<name>.md`) and
inherit every choice here.

## Cryptographic substrate

### Proving system: Groth16

```text
proving_system = Groth16
```

The decisive constraint: **Sui has a native Groth16-on-BN254
verifier in Move**. PLONK / Halo2 / STARK proofs would require
either a Move-side verifier (significant implementation cost,
no shipped reference) or off-chain verification (defeats the
on-chain trust story).

Groth16 has known trade-offs that this protocol accepts:

- **Per-circuit trusted setup.** Each circuit needs its own
  proving key (PK) and verifying key (VK), generated by a
  ceremony or a development setup. PKs are persisted as
  deployment artifacts (see § Artifact discipline).
- **Public-input count is performance-sensitive on Sui.** Sui's
  Groth16 verifier caps public inputs at **8 field elements**.
  Circuits that logically need more inputs MUST compress via a
  Poseidon hash of the extras (the "signal hash" pattern, see
  § Public-input compression).
- **Fixed circuit shape.** A circuit cannot conditionally
  enable/disable constraints. Branches are encoded as selectors
  multiplied into both branches' constraints. This is a constant
  reminder that circuits are not programs.

### Curve: BN254

```text
curve = BN254 (a.k.a. alt_bn128)
scalar_field = Fr (254-bit prime)
base_field   = Fq (254-bit prime, the field Baby Jubjub coordinates live in)
```

The pairing-friendly curve Groth16 is instantiated over. **Same
curve the native `crypto` crate already pins** — `Fq` in the
gadget world IS the field that holds Baby Jubjub coordinates, the
Poseidon hash outputs, and every protocol value pinned in
`specs/babyjub-*.md`. Gadgets and natives operate on the same
type; no field conversion at the boundary.

The two prime fields:

- **`Fq`** — BN254's base field. Every value in the protocol's
  native specs lives here. **Public-input and witness fields of
  every circuit are `Fq` elements.**
- **`Fr`** — BN254's scalar field, used internally by Groth16
  for proof construction. Application code never touches `Fr`
  directly; the `prover` crate's API takes `Fq` values.

> **NOTE on naming.** Arkworks calls the scalar field of BN254
> `Fr` and the base field `Fq`. The naming clashes with our
> native crate, which already uses `Fq` for "the field Baby
> Jubjub coordinates live in" — which IS BN254's base field.
> The two `Fq`s are the same field. The native crate's `Fr`
> (the Baby Jubjub scalar field, `ark-ed-on-bn254`'s `Fr`) is a
> different prime and is **not** Groth16's scalar field. The
> gadget crate will import names explicitly to avoid this
> bleeding into ambient confusion.

### Poseidon parameters: circomlib

```text
poseidon_variant = circomlib (light-poseidon parameters)
```

The native `crypto::poseidon` module uses **circomlib's Poseidon
parameters** via the `light-poseidon` crate. Arkworks' default
Poseidon (`ark-crypto-primitives::sponge::poseidon`) uses
*different* parameters and produces *different* outputs on the
same input. **The gadget side MUST reproduce circomlib's
parameters, not arkworks' defaults**, or the native↔circuit
equivalence breaks silently.

This is the single largest engineering cost imposed by the stack
choice: the Poseidon gadget cannot be a thin wrapper around
`PoseidonSpongeVar`. It must be a from-scratch implementation of
the permutation against `FpVar<Fq>` using circomlib's round
constants and MDS matrix, loaded from `light-poseidon`'s shipped
parameter sets. The native↔circuit equivalence test (see §
Equivalence discipline) is the load-bearing artifact that
guarantees the gadget didn't drift from the native.

The cost is one-time. The benefit is that `crypto`, the TS SDK
(which uses `poseidon-lite`, also circomlib-parameterized), and
the circuit all compute the same Poseidon — which is what makes
the three-way protocol coherent. Arkworks-default Poseidon would
break TS↔Rust interop, which is non-negotiable.

## Library substrate

### Arkworks 0.5

Pinned versions:

```toml
ark-ff             = "0.5"
ark-ec             = "0.5"
ark-bn254          = "0.5"
ark-ed-on-bn254    = "0.5"
ark-serialize      = "0.5"
ark-std            = "0.5"
ark-relations      = "0.5"
ark-r1cs-std       = "0.5"
ark-snark          = "0.5"
ark-groth16        = "0.5"
ark-crypto-primitives = "0.5"
```

**Reason for 0.5, not 0.4.** The native `crypto` crate already
pins 0.5. Two versions of `ark-bn254` in the workspace would
produce two distinct `Fq` types — same field mathematically,
incompatible at the type level. The native↔circuit equivalence
tests, which are the load-bearing tests for every gadget, depend
on the native `Fq` and the circuit's witness `Fq` being the same
type. One version, workspace-wide.

The arkworks 0.4 → 0.5 API drift (`ark-r1cs-std` trait
reshuffling, `ark-crypto-primitives::sponge` reorganization,
`ark-groth16` setup/prove/verify surface) does not affect the
proving-system semantics; only call sites shift. Gadgets and
circuits will be written 0.5-native from the start.

### Why not `ark-crypto-primitives::sponge::poseidon`

It's the obvious choice and would be wrong here. See § Poseidon
parameters: the parameter sets do not match circomlib. Using it
would silently break TS interop and break compatibility with
every fixture pinned in the native protocol specs.

### Companion crates

```toml
light-poseidon = "<same version as the native crate>"
```

Loaded only for its **parameter sets** (`bn254_x5`'s round
constants and MDS matrices). The native crate uses
`light-poseidon` to compute the hash directly; the gadget crate
uses it as the canonical source of parameters and reimplements
the permutation against `FpVar<Fq>`. Both call sites pin the
same version, so any future parameter tweak (extremely
unlikely — circomlib parameters are stable) propagates to both
sides together.

## Conventions

### Equivalence discipline

**Every gadget ships with a native↔circuit equivalence test.**
This is the load-bearing test discipline; it is what guarantees
the gadget did not drift from the native primitive it mirrors.

The test shape, for a gadget `f_var` mirroring native `f`:

```rust
#[test]
fn f_var_matches_native() {
    let cs = ConstraintSystem::<Fq>::new_ref();
    let inputs_native: Vec<Fq> = /* ... */;
    let expected = crypto::f(&inputs_native);

    let inputs_var: Vec<FpVar<Fq>> = inputs_native
        .iter()
        .map(|x| FpVar::new_witness(cs.clone(), || Ok(*x)))
        .collect::<Result<_, _>>().unwrap();
    let got_var = f_var(cs.clone(), &inputs_var).unwrap();

    let expected_var = FpVar::new_input(cs.clone(), || Ok(expected)).unwrap();
    got_var.enforce_equal(&expected_var).unwrap();
    assert!(cs.is_satisfied().unwrap());
}
```

A gadget without this test is not a complete brick. The test is
checked into source; CI runs it.

### Circuit `empty()` constructor

Every `ConstraintSynthesizer` impl ships an `empty()` (or
`for_setup()`) constructor that produces a circuit with dummy
`Option::Some(default)` witness values. Required because trusted
setup needs a circuit instance to extract the constraint
structure, but the real witnesses don't exist yet. Dummy values
must satisfy the structural constraints (e.g. an SMT
membership-proof circuit's dummy must have correct tree depth)
so setup produces a usable PK.

### Public-input compression: the signal-hash pattern

Sui's Groth16 verifier caps public inputs at **8 `Fq` elements**.
Circuits that logically have more public inputs MUST collapse
the excess into a single Poseidon-hashed "signal" public input:

```text
signal = Poseidon(domain, [param_1, param_2, ..., param_n])
```

The Move-side verifier reconstructs `signal` from the
authoritative on-chain values of `param_1..n` and passes it
alongside the proof. The circuit takes `signal` as a public
input and binds it by re-hashing inside the circuit. A subset
of parameters that the chain MUST be able to bind directly
(e.g. an object id, a recipient address, a registry root) stays
as its own public input.

Each circuit's spec must specify, at design time:

- How many public inputs (≤ 8).
- Which inputs are direct vs. compressed via signal hash.
- The signal hash's domain tag and input ordering.

### Endianness at the on-chain boundary

Sui object IDs and certain on-chain bytes arrive **big-endian**.
Arkworks' `Fr::from_le_bytes_mod_order` expects little-endian.
Cross-boundary parsing MUST be explicit: `parse_fr_be` for Sui
object IDs, `parse_fr_le` for blindings and other off-chain-
originating field elements. This matches the convention the
native `babyjub::wire` module already uses; the prover-server's
HTTP handler layer enforces it on inbound payloads.

### No `tracing_subscriber` in the prover hot path

A documented gotcha from prior work: enabling
`tracing_subscriber` with default thread-local context tanks
Groth16 prove throughput by ~400× (15ms → 6s+) due to
interaction with Rayon's work-stealing scheduler. The
`prover-server` binary uses plain `println!` for logs and
explicitly does NOT install a tracing subscriber. Other crates
in the workspace are free to use `tracing`; only the prover
hot path is exempt.

### Artifact discipline

- **Proving keys and verifying keys are NOT source-controlled.**
  Generated on first boot of `prover-server` (or via the
  `export-vks` binary) and written to `keys/`.
- **Verifying keys ARE deployment artifacts.** The `export-vks`
  binary produces the byte-blob the Move-side verifier needs;
  publishing it to chain is a deploy step.
- **Trusted setup randomness.** Development setup uses a
  reproducible deterministic seed for local iteration; the
  spec for any production deployment will pin a real ceremony
  protocol (Powers of Tau or equivalent). The current stack
  does not commit to a specific ceremony; that is a future spec.

### Crate boundary discipline

Same shape as the native side:

- **`crates/gadgets`** — constants, parameter loaders, gadget
  free functions returning `Result<FpVar<Fq>, SynthesisError>`,
  and the native↔circuit equivalence tests. Depends on `crypto`
  for the native references.
- **`crates/circuits`** — one `ConstraintSynthesizer` impl per
  provable claim. Composes gadgets. Encoding-specific circuit
  adapters live in submodules
  (`circuits::encodings::text_utf8_v1`, etc.).
- **`crates/prover`** — owns setup, prove, verify. Persists PKs
  and VKs. Two binaries: `export-vks`, `circuit-stats`. **Does
  NOT depend on `wasm-bindgen`** so it stays native-compilable
  for the server.
- **`crates/prover-server`** *(later)* — Axum HTTP wrapper.
  `POST /prove/<circuit>` with public/private inputs.
- **`crates/prover-wasm`** *(deferred)* — `wasm-bindgen`
  wrapper. Will exist; not on the critical path. See § Deferred
  for the case.

## Deferred

- **In-browser proving (`crates/prover-wasm`).** Groth16 in WASM
  is real but slow (often 10–60× slower than native). Proving
  keys are megabytes and must ship to the browser. The HTTP
  server path is faster, simpler, and the default. WASM proving
  is an opt-in escape hatch for users who reject server trust
  or for offline / no-network demos. Build after at least one
  circuit and the server are working.
- **Production trusted-setup ceremony.** Dev setup is
  deterministic and reproducible; production needs a real
  ceremony spec. Future doc.
- **Recursive proofs / proof aggregation.** Not in scope. If
  ever needed, the stack choice (Groth16 + BN254) is compatible
  with on-chain proof composition via additional pairing
  checks, but no current circuit needs it.
